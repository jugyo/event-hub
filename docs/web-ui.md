# Web UI Design Guidelines

This document defines the architecture, API contract, update behavior, UI implementation, testing, and security standards for the initial Web UI. `REQUIREMENTS.md` remains the source of truth, and this design does not change the host, plugin, or event store boundaries defined in `docs/architecture.md`.

## Scope

The initial Web UI is a localhost-only, read-only React SPA started through an event-hub command. Its display scope is limited to:

- load state and plugin-scoped diagnostics for sources and consumers;
- the most recent execution time and result for each plugin;
- pending work, including `pending` and `retry_wait`;
- failure details expressed through fixed public error codes and messages with secrets removed; and
- stored event history.

Operational actions and configuration changes are out of scope, including running a tick, retrying work, changing state, adding, editing, or deleting plugins or schedules, and managing secrets. Viewing event history does not change delivery state, redeliver events, or replay historical events.

The deliverable governed by this document is the design document only. The Web UI, HTTP server, REST API, and build pipeline must be implemented in separate changes.

## Architecture and Responsibility Boundaries

### Delivery and Startup

- Implement the frontend with React and TypeScript as a single-page application built by Vite.
- The event-hub HTTP server serves both the static files generated by Vite and the JSON REST API from the same origin. The Vite development server does not run in production.
- The HTTP server explicitly binds to either the IPv4 address `127.0.0.1` or the IPv6 address `::1`. It must not rely on defaults or bind to `0.0.0.0`.
- Keep the frontend separate from the event-hub command process through the static asset and API client boundaries. The frontend never communicates directly with plugin processes.

### Layer Responsibilities

| Layer                             | Responsibilities                                                                           | Out of scope                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| React SPA                         | Presentation, filter and paging input, loading, empty, and error states, and accessibility | Direct storage access, inferring domain state, or retrieving secrets              |
| TanStack Query                    | Server state from the REST API, caching, polling, retries, and refetching                  | Persistent state or UI-local state such as disclosure state and in-progress input |
| JSON REST API                     | Query validation, application service calls, and conversion to public DTOs and errors      | Plugin execution, state mutation, or generating frontend HTML                     |
| Application service / event store | Reading plugin status and event history                                                    | Types that depend on HTTP or React                                                |
| Plugin process                    | Existing source and consumer processing                                                    | Direct communication with the Web UI or HTTP server                               |

UI components must not treat REST response types as storage rows or internal `@jugyo/duex` types. The API adapter converts internal state into the secret-free DTOs defined by this document.

### Dependencies

Use React, Vite, MUI, and TanStack Query as the frontend foundation. MUI is the basis for shared components and theming, while TanStack Query is the only retrieval and caching layer for server state. Do not introduce another global state library. Store filters that must survive navigation in URL search parameters and keep local display state in React state.

## REST API Contract

The API base path is `/api/v1`, and responses use `Content-Type: application/json`. The initial API exposes read-only `GET` endpoints only. An unknown query parameter produces `400 INVALID_QUERY` rather than being interpreted ambiguously.

### Common Representations

- Represent every timestamp as a UTC ISO 8601 string, for example `2026-09-24T01:02:03.456Z`.
- Return `null`, rather than omitting an optional field, when its value is absent. Return an empty array as `[]`.
- Treat IDs and error codes as opaque strings.
- Use `{ "error": { "code": string, "message": string, "details": object | null } }` for public error responses.
- `message` is a fixed public message and never copies plugin exceptions, stacks, arbitrary error details, or environment variable values. Limit `details` to enumerated, non-secret information such as input field names.
- Use `400` for validation failures, `404` when a resource does not exist, and `500 INTERNAL_ERROR` with a fixed message for unexpected failures.

### Plugin List

`GET /api/v1/plugins` returns sources and consumers together.

```json
{
  "plugins": [
    {
      "id": "github-source",
      "kind": "source",
      "loadState": "loaded",
      "lastRun": {
        "startedAt": "2026-09-24T01:00:00.000Z",
        "finishedAt": "2026-09-24T01:00:01.000Z",
        "status": "completed"
      },
      "pendingWork": 0,
      "failure": null,
      "diagnostics": []
    }
  ]
}
```

`kind` is `source | consumer`, `loadState` is `loaded | invalid | missing | disabled`, and execution `status` is `running | completed | failed`. `lastRun` is `null` when no execution exists, and `finishedAt` is `null` while an execution is running. `failure` and `diagnostics` use `{ "code": string, "message": string, "occurredAt": string }`. `pendingWork` is a non-negative integer and, for a consumer, is the total of `pending` and `retry_wait` as required by the existing specification.

### Plugin Details

`GET /api/v1/plugins/{pluginId}` returns the same plugin object as the list endpoint under `plugin`. It may additionally return `pendingWorkBreakdown` with separate `pending` and `retry_wait` counts, the most recent failure, and a diagnostic list. It never returns ordinary plugin configuration, environment variable mappings, secret reference names, journals, step results, or stacks.

### Event History

`GET /api/v1/events` returns stored events in descending `occurredAt` order and descending `id` order for equal timestamps. It accepts the following query parameters.

| Parameter  | Required | Rule                                                                   |
| ---------- | -------- | ---------------------------------------------------------------------- |
| `from`     | no       | UTC ISO 8601. When present, `occurredAt >= from`                       |
| `to`       | no       | UTC ISO 8601. When present, `occurredAt < to`                          |
| `type`     | no       | Exact event type match. Repeat the parameter to specify multiple types |
| `sourceId` | no       | Exact source ID match                                                  |
| `limit`    | no       | Default `100`, minimum `1`, maximum `500`                              |
| `cursor`   | no       | An opaque cursor returned by the server                                |

The window formed by `from` and `to` is the half-open interval `[from, to)`. When both are present, `from < to` is required. This query reads stored history and does not apply the default 24-hour source backfill limit.

```json
{
  "events": [
    {
      "id": "evt_01",
      "sourceId": "github-source",
      "type": "github.change",
      "externalId": "123",
      "schemaVersion": 1,
      "occurredAt": "2026-09-24T00:59:00.000Z",
      "observedAt": "2026-09-24T01:00:00.000Z",
      "payload": {}
    }
  ],
  "page": {
    "nextCursor": null,
    "limit": 100
  }
}
```

The cursor must allow the server to validate the filters, sort keys, and final row, while remaining opaque to the client. Request the next page with the same filters and `limit`. An invalid cursor or one that does not match the filters produces `400 INVALID_CURSOR`. The initial UI does not request an unlimited result set or use offset pagination.

The event `payload` is displayed as part of the event contract, so a source must never store secrets in it. The API neither supplements nor expands known credential fields, and access logs never record response bodies.

## Updates and Failure Behavior

Poll the plugin list and the visible plugin details every five seconds. Fetch event history when filters are applied, the user changes pages, or the user requests a refresh; do not poll it automatically. This keeps the user's position stable while browsing history.

The shared TanStack Query rules are:

- Stop interval fetches while `document.visibilityState !== "visible"`.
- When the tab becomes `visible` again, immediately invalidate and refetch visible queries.
- Immediately refetch visible queries after network reconnection.
- Retry only network failures and `500`, `502`, `503`, and `504` responses automatically, waiting one second after the first failure, two seconds after the second, and four seconds before the final attempt, for a maximum of three retries.
- Do not retry `400` or `404` automatically. When `Retry-After` is present, prefer it if it specifies a longer delay.
- Retain the last successful data after a polling failure, and show that it may be stale together with the time of the last successful update. Resume fetching at the next normal interval even after exhausting retries.
- Share feature-level query definitions instead of implementing separate requests in each component for the same query key.

## React Structure and Implementation Rules

Use the following structure as the baseline for the initial implementation.

```text
src/web/
  app/          # router, providers, theme, and page layout
  api/          # HTTP client, public DTOs, and error conversion
  features/
    plugins/    # queries, list, details, and diagnostic presentation
    events/     # queries, filters, history table, and paging
  components/   # shared, domain-independent presentation
  test/         # test setup, fixtures, and request handlers
```

Page components compose routes and query parameters, while each feature component has one presentation purpose. Keep HTTP calls inside `api/` and feature query definitions; presentational components never call `fetch` directly. Do not combine everything into one large status page. Separate the plugin list, plugin details, and event history into routes or clearly defined sections.

### MUI

- Use MUI theme tokens for color, spacing, typography, and breakpoints rather than scattering custom design values across components.
- Never communicate status through color alone. Pair it with a text label and, where appropriate, an icon.
- Wrap an MUI component only when adding shared behavior or event-hub-specific meaning.
- On narrow viewports, make desktop tables horizontally scrollable or provide cards that retain essential information. Do not leave content invisibly outside the viewport.

### Loading, Empty, and Error States

- For initial loading, display a skeleton or progress indicator close to the size of the target region with an accessible name that communicates loading.
- Distinguish a successful empty array from an error and display an empty-state message that supports the user's next decision, such as “No plugins found” or “No events match these filters.”
- Display an error within the affected region using a fixed public message and a retry control. Do not replace the entire page unnecessarily, and preserve previously fetched data when available.
- During a background refetch, keep existing content instead of replacing it with a skeleton, and indicate the update non-disruptively.

### Accessibility

- Make navigation, filtering, paging, and retry controls operable using only a keyboard, and never remove focus indicators.
- Use heading levels, landmarks, and table headers in semantic order. Use an appropriate button or link instead of a clickable `div`.
- Associate every form control with a visible label, and programmatically associate validation errors with their controls.
- Use an appropriate live region for dynamic errors and update completion without repeatedly announcing routine polling.
- Ensure the normal MUI theme and error and status representations meet WCAG 2.2 AA contrast requirements, and preserve primary controls and content at 200% zoom and on narrow viewports.
- Preserve a machine-readable UTC timestamp. If the UI also displays local time, allow users to inspect the UTC value and state that filter boundaries use UTC.

## Testing Strategy

Use Vitest, React Testing Library, `@testing-library/user-event`, and a DOM environment for frontend unit and component tests. In component tests that do not require a real HTTP server, use Mock Service Worker to stub the network boundary. Do not mock TanStack Query itself or MUI internals.

Unit tests cover pure rules, including query parameter encoding and validation, UTC and half-open interval boundaries, cursor and page state, public API error conversion, and visibility and retry policies. Component tests cover loading, empty, success, error, and stale-data states; keyboard operation; filtering and paging; stopping polling while hidden; and immediate refresh when visible again. Use fake timers for timer-dependent tests.

API tests run at the boundary between the HTTP adapter and application service. They verify status codes, response schemas, result limits, cursors, `[from, to)` over `occurredAt`, plugin-scoped diagnostics, read-only behavior, fixed error messages, and non-exposure of secrets. Existing storage tests cover event store queries and retention; frontend tests must not duplicate those checks against a real database.

Browser end-to-end tests are not part of the initial baseline. When implementation begins, include unit, component, and API tests in the standard CI and add tests for every changed layer in the same change.

## Security and Operational Boundaries

Because the server binds only to loopback, the initial HTTP server and API have no authentication. This assumption does not permit remote access. Any change involving exposure outside loopback through a reverse proxy, LAN access, container port forwarding, or another mechanism requires a separate threat model and design decision covering authentication, authorization, CSRF, origin policy, and TLS.

Never expose secret values through the API, HTML, client-side state, browser console, server logs, access logs, diagnostics, or telemetry. In particular, never expose:

- environment variable values passed to plugin processes;
- secret backend values, secret reference names, or host-to-plugin mappings;
- plugin exception messages, stacks, or arbitrary details;
- credential-like values accidentally placed in ordinary configuration; or
- dumps of journals, step inputs or results, process environments, or request or response bodies.

The HTTP server registers no mutating endpoints and never connects unknown routes to application operations. SPA fallback applies only to asset `GET` requests; an unknown `/api/` route must not succeed with an HTML response.
